# 文件系统简化改造方案

## 1. 结论

聊天记录的核心方向是正确的：前端负责业务模型与业务编排，后端主要提供浏览器缺失的持久化、文件系统和跨域能力。

但不建议把后端直接退化为“任意路径文件读写 + 任意 URL 请求代理”。更合适的方案是：

> 前端拥有业务数据结构；后端提供按资源 ID 注册的通用存储能力，并对任务、密钥、二进制文件和本机目录保留专用服务。

这样既能消除大量重复 CRUD，又不会失去数据一致性、文件生命周期和基本安全边界。

## 2. 现状判断

当前项目的数据可以分成四类，不能完全用同一种接口处理。

| 数据类型         | 当前代表                          | 建议归属          |
| ---------------- | --------------------------------- | ----------------- |
| 前端业务数据     | 模板、小说、TTS 项目              | 通用文档/集合存储 |
| 后端运行状态     | 生图任务、日志、哈希缓存          | 后端专用服务      |
| 后端消费的配置   | API Key、Base URL、模型 ID        | 注册式配置服务    |
| 二进制及本机文件 | 图片、音频、媒体目录、Ren'Py 同步 | 专用文件能力      |

### 2.1 当前实现的主要问题

#### ConfigJson 会产生“假成功”（已修复）

已在第二阶段修复，详见 §11 进度。`ConfigJson` 现基于 `src/server/common/storage/json-file.ts` 的原子写入：写盘失败抛错（接口返回 500，不再假成功）、默认值深合并、`get()` 返回深拷贝、损坏文件改名为 `.corrupt-<时间戳>` 后回退默认值。

遗留：仍使用同步文件 API，会阻塞事件循环。配置体积小且调用方均为同步签名，待配置迁入异步 SettingsRegistry（§7.3）时一并解决。

#### 通用列表存在并发覆盖和数据丢失风险

`TaskManager`、`TemplateManager`、TTS 项目都采用“读取整个 JSON → 修改 → 写回整个 JSON”的方式，但没有资源级串行队列、版本检查和原子写入。

两个并发请求可能读取同一个旧版本，随后后写入者覆盖先写入者的修改。

同时，任务和模板读取失败时会返回空数组。如果只是临时读取失败或 JSON 损坏，下一次修改可能把空数组写回，从而把“读取异常”变成真正的数据丢失。

相关代码：

- `src/server/common/task-manager/index.ts`
- `src/server/common/template-manager/index.ts`
- `src/server/module/tts/project.ts`

#### TaskManager 混合了存储和业务副作用

`TaskManager` 不只是保存任务列表，它还知道：

- GPT 图片的尺寸和质量类型；
- 模板的完整数据结构；
- 生成图片的目录和 URL 规则；
- 删除任务时是否同时删除图片；
- 服务重启后如何处理运行中的任务；
- 如何通过事件通知前端。

因此任务不能简单替换为允许前端任意修改的通用列表。任务数据由后端生成和消费，应继续由后端服务控制状态流转。

#### 小说模块方向正确，但 CRUD 仍然过细

小说模块已经把提示词组装、上下文选择和生成编排放到了前端，后端主要提供持久化和 LLM 代理，这与本方案的方向一致。

但后端仍分别实现了小说、文本和章节 CRUD，了解 `title`、`chapterId`、`sourceIds` 等业务字段。删除章节还在后端执行文本级联删除。

此外，每次写入小说都先更新 `novel.json`，再更新 `index.json`。两个文件不是事务性的，任意一步失败都可能使索引与正文不一致。

相关代码：

- `src/server/module/novel/store.ts`
- `src/server/module/novel/types.ts`
- `src/server/api/novel.ts`

#### TTS 项目接口没有形成有效边界

TTS 项目更新接口使用 `z.any()` 接收任意数据。这实际上已经不提供业务校验，却仍然保留了一整套业务专用 CRUD，既没有获得通用接口的简洁性，也没有获得专用接口的可靠约束。

相关代码：`src/server/api/tts/index.ts`。

#### 静态图片不是普通文件存储

图片模块除了读写文件，还包含：

- 图片格式验证与 WebP 转换；
- 尺寸限制与压缩；
- 内容哈希去重；
- 缩略图生成与缓存；
- 模板、任务引用分析；
- 未引用图片清理；
- 打开系统目录。

这部分具有明确的二进制资源生命周期，不适合替换为通用 JSON 存储。

相关代码：`src/server/common/static/index.ts`。

#### 媒体整理必须保留文件路径安全边界

媒体整理模块需要访问用户选择的任意本机目录，当前已经实现了绝对路径验证和子路径约束。这些限制不能因为程序主要在本地运行就取消。

相关代码：`src/server/module/media-classifier/index.ts`。

#### 本地应用仍然需要安全边界

项目会计算并向前端提供局域网访问地址，因此不能假定后端永远只由当前桌面用户访问。局域网中的其他设备、恶意网页、浏览器扩展或 XSS 都可能尝试调用本地服务。

相关代码：

- `src/server/index.ts`
- `src/server/api/common/config.ts`

## 3. 推荐的总体架构

### 3.1 明确业务归属

推荐遵循以下规则：

- 前端决定字段、业务规则、数据组合关系和业务迁移。
- 后端决定数据保存位置、原子写入、版本冲突、资源大小限制和文件权限。
- 后端会消费的数据，后端必须知道其必要结构。
- 只有前端消费的数据，才使用完全无业务字段假设的通用存储。

“后端不知道具体字段”适用于模板、小说内容、TTS 项目等前端拥有的数据，但不适用于任务状态、API 密钥、图片引用和媒体文件操作。

### 3.2 新增统一存储基础层

建议目录：

```text
src/server/common/storage/
  data-path.ts
  json-file.ts
  registry.ts
  document-store.ts
  collection-store.ts
  entity-store.ts
  change-bus.ts
  errors.ts
```

各文件职责如下：

- `data-path.ts`：统一管理 `data` 根目录，消除散落的 `process.cwd()`。
- `json-file.ts`：JSON 读取、原子写入、备份和损坏文件恢复。
- `registry.ts`：将公开资源 ID 映射到固定存储位置和存储驱动。
- `document-store.ts`：保存单个 JSON 文档。
- `collection-store.ts`：保存小型 JSON 列表。
- `entity-store.ts`：每个实体单独保存一个文件，并提供摘要列表。
- `change-bus.ts`：统一发布资源变更事件。
- `errors.ts`：定义不存在、版本冲突、数据损坏等结构化错误。

> 进度：前两者与 `errors.ts`、`resource-lock.ts`（资源级串行队列）已在第一阶段实现；`registry.ts` 及三种 Store、`change-bus.ts` 随第三、四阶段落地。

存储基础层应满足以下要求：

- 客户端只能传资源 ID，不能传真实文件路径。
- 同一资源的读改写进入串行队列。
- 写入采用临时文件和替换操作，避免进程中断留下半个 JSON。
- 写入前保留最近一次有效备份。
- JSON 损坏时返回明确错误，不返回空对象或空数组。
- 限制 JSON 深度、请求体大小、集合数量和单项大小。
- 所有修改产生单调递增的 `revision`。
- `updatedAt` 仅用于展示和排序，不用于并发控制。

资源注册示例：

```ts
storageRegistry.register('image.templates', {
  kind: 'collection',
  file: dataPath('images', 'templates.json'),
})

storageRegistry.register('novel.books', {
  kind: 'entity',
  dir: dataPath('novels', 'books'),
})

storageRegistry.register('tts.projects', {
  kind: 'entity',
  dir: dataPath('tts', 'projects'),
})
```

`image.templates` 是能力 ID，不是磁盘路径。后端只知道它对应什么存储驱动和保存位置，不需要知道模板包含哪些字段。

## 4. 三种通用存储模型

### 4.1 DocumentStore

适合模块设置、工作区状态等单对象数据。

```ts
interface StoredDocument<T = unknown> {
  revision: number
  updatedAt: number
  value: T
}
```

建议使用整体替换，而不是默认使用浅层 `PATCH`。整体替换能准确表达字段删除，也能避免后端猜测嵌套对象的合并语义。

### 4.2 CollectionStore

适合图片模板等数量有限的小型列表。

```ts
interface StoredItem<T = unknown> {
  id: string
  revision: number
  createdAt: number
  updatedAt: number
  value: T
}
```

后端只管理 `id`、`revision`、`createdAt` 和 `updatedAt`，`value` 完全由前端定义。

### 4.3 EntityStore

适合小说和 TTS 项目。每个实体独立保存一个文件，列表只返回摘要，无需加载所有正文。

```ts
interface StoredEntity<T = unknown, S = unknown> {
  id: string
  revision: number
  createdAt: number
  updatedAt: number
  summary: S
  value: T
}
```

`summary` 也由前端提供，后端不需要知道 `title`、`chapterCount` 等字段。小说列表可以直接读取实体信封中的摘要，从而取消容易不一致的 `index.json`。

## 5. 通用接口设计

建议统一挂载在 `/api/storage`。

```text
GET    /api/storage/documents/:resource
PUT    /api/storage/documents/:resource

GET    /api/storage/collections/:resource
POST   /api/storage/collections/:resource
PUT    /api/storage/collections/:resource/:id
DELETE /api/storage/collections/:resource/:id
POST   /api/storage/collections/:resource/batch

GET    /api/storage/entities/:resource
POST   /api/storage/entities/:resource
GET    /api/storage/entities/:resource/:id
PUT    /api/storage/entities/:resource/:id
DELETE /api/storage/entities/:resource/:id

GET    /api/storage/events?resources=image.templates,novel.books
```

### 5.1 版本控制

更新请求携带期望版本：

```json
{
  "expectedRevision": 12,
  "value": {},
  "summary": {}
}
```

版本不一致时返回 `409 Conflict`，并携带服务端当前版本或最新数据。

不建议使用聊天记录中的 `updatedTime` 判断脏数据，因为：

- 多次写入可能产生相同时间戳；
- 系统时间可能回拨；
- 客户端与服务端时钟可能不一致；
- 时间戳不能可靠表达写入先后关系。

`revision` 应由后端在成功提交后单调递增。

### 5.2 批量操作

模板文件夹重命名等操作需要一次修改多个条目，可以提供通用批处理：

```json
{
  "expectedRevision": 18,
  "operations": [
    {
      "type": "replace",
      "id": "template-id",
      "value": {}
    }
  ]
}
```

整个批次在资源锁内只写一次文件，避免逐项请求产生半完成状态。

### 5.3 统一响应结构

成功响应：

```json
{
  "success": true,
  "data": {},
  "revision": 13
}
```

错误响应：

```json
{
  "success": false,
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "数据已被其他页面修改",
    "currentRevision": 13
  }
}
```

不要继续在底层捕获错误后返回空数组。读取失败、解析失败、不存在和版本冲突必须是不同的错误状态。

## 6. 格式校验的归属

原聊天记录中“本地后端不需要格式校验”不建议完全采纳。应分成三层：

1. 存储层始终校验信封结构，包括资源 ID、revision、JSON 类型和数据大小。
2. 前端拥有的数据由前端的 Zod schema 校验和迁移。
3. 后端需要消费的数据，在资源注册处提供一次 schema，接口层不再重复字段定义。

共享的业务 schema、类型和常量建议放在：

```text
src/shared/schema/
src/shared/storage/
```

前后端引用同一个 schema，而不是分别定义一遍。

当前 `src/server/module/gpt-image/config.ts` 直接导入了前端的接入点定义，这属于层级倒置。接入点类型、默认配置和无 UI 依赖的常量应移动到 `src/shared`。

## 7. 各模块具体改造

| 模块               | 推荐改造                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 图片模板           | 改为 `CollectionStore('image.templates')`；字段和文件夹重命名逻辑移到前端                        |
| 图片生成           | 前端提交完整模板快照，不再只提交 `templateId`；后端只负责调用模型、保存图片和创建任务            |
| 图片任务           | 保留 `TaskService`；底层可复用 CollectionStore，但前端不能任意修改任务状态                       |
| GPT/TTS/Novel 配置 | 使用注册式 `SettingsRegistry`，schema、defaults 和密钥策略集中定义，使用通用设置路由             |
| 小说               | 改为 `EntityStore('novel.books')`；章节级联、文本 CRUD、摘要计算全部在前端完成，一次保存完整小说 |
| TTS 项目           | 改为 `EntityStore('tts.projects')`；取消 `z.any()` 项目更新接口                                  |
| Ren'Py 同步        | 保留专用接口，只接收明确的工作目录和待同步文件描述，不读取整个 TTS 项目存储                      |
| 静态图片           | 保留专用 AssetService，继续负责压缩、哈希、缩略图、引用与清理                                    |
| 音频输出           | 保留专用接口，并完善 Range 和文件名约束                                                          |
| media-classifier   | 保留专用 WorkspaceService；`state.json` 可使用 DocumentStore，但扫描、删除和路径检查不能通用化   |
| 日志和哈希缓存     | 后端内部数据，不开放到通用写接口                                                                 |
| UI 偏好            | 主题、弹窗选项等继续使用 localStorage，无需强制搬到后端                                          |

### 7.1 图片模板与生成接口

模板是前端拥有的数据，适合直接迁移到通用集合。

当前生图接口只接收 `templateId`，导致后端必须读取模板并理解模板结构。建议改为由前端提交一次生成所需的完整快照：

```ts
interface GenerateImageRequest {
  input: {
    prompt: string
    images: string[]
    aspectRatio?: string
    n?: number
  }
  size: string
  quality: string
  appendAspectRatio?: boolean
}
```

任务中的 `rawTemplate` 也应改名为 `inputSnapshot` 或 `requestSnapshot`，明确它只是任务创建时的不可变快照，而不是对模板存储的引用。

### 7.2 TaskManager 拆分

建议拆成两个层次：

```text
TaskRepository
  只负责任务记录的可靠持久化

TaskService
  创建任务
  状态流转
  服务重启后的任务恢复
  删除任务及输出文件
  发布任务事件
```

`TaskRepository` 可以复用通用 JSON 存储引擎，但不应将任务资源开放成前端可任意写入的 CollectionStore API。

任务状态变更必须通过 `TaskService`，以保证状态、错误信息、输出文件和 SSE 通知保持一致。

### 7.3 配置与密钥

模块配置不能全部视为前端私有数据，因为后端调用模型时必须读取 API Key、Base URL 和模型 ID。

建议在通用存储引擎之上增加 `SettingsRegistry`：

```ts
settingsRegistry.register('gpt-image', {
  defaults: defaultGptImageSettings,
  schema: gptImageSettingsSchema,
  secretKeys: ['apiKey'],
})
```

路由只实现一次：

```text
GET /api/settings/:id
PUT /api/settings/:id
```

具体字段只在注册定义中出现一次，不再分别出现在配置类、API schema 和前端重复类型中。

密钥建议遵循以下规则：

- GET 默认只返回掩码或 `configured: true`。
- 空值表示不修改密钥，显式操作用于清除密钥。
- 密钥由后端注入外部请求，不发送给普通前端页面。
- 现有密钥数据通过一次迁移转换为新的密钥存储格式。

### 7.4 小说

小说适合使用 EntityStore：

```text
data/novels/books/<novelId>.json
```

实体的 `value` 保存完整小说，`summary` 保存列表所需的信息：

```ts
interface NovelSummary {
  title: string
  chapterCount: number
}
```

前端负责：

- 新增、修改和删除文本；
- 新增和修改章节；
- 删除章节时级联移除对应文本；
- 生成并更新摘要；
- 校验章节和文本之间的引用；
- 业务 schema 迁移。

后端只负责保存整个实体、检查 revision 和维护通用信封元数据。这样可以删除大量小说字段级 API，并取消 `index.json` 与 `novel.json` 的双写。

### 7.5 TTS 项目

TTS 项目也适合 EntityStore。角色、对白和备注的增删改全部由前端完成，然后整体保存项目。

与后端文件系统相关的操作单独保留：

- 音频生成和保存；
- 音频读取和 Range 响应；
- Ren'Py 工作目录验证；
- 文件同步。

Ren'Py 同步接口只接收完成同步所需的最小参数，不应为了获取 `renpyExportDir` 而让后端重新依赖完整 TTS 项目结构。

### 7.6 图片和媒体文件

图片与媒体模块不应开放任意路径读写接口。

可以在内部抽象 `AssetStore`，统一处理：

- 注册桶 ID 与真实目录的映射；
- 文件名和 MIME 类型检查；
- 内容哈希；
- 二进制流式读取；
- 缩略图缓存；
- 删除和清理。

但外部 API 仍按图片上传、图片清理、媒体工作区等能力提供，避免客户端获得任意文件系统权限。

## 8. 外部请求代理

不建议开放如下形式的接口：

```json
{
  "url": "任意地址",
  "method": "任意方法",
  "headers": {},
  "body": {}
}
```

这会成为任意网络访问、内网探测和密钥转发入口。

### 8.1 注册式请求中继

可以实现受限的请求中继注册表：

```ts
requestRegistry.register('novel.openai', {
  resolveOrigin: getNovelBaseUrl,
  allowedMethods: ['POST'],
  allowedPaths: ['/chat/completions'],
  injectCredential: getNovelApiKey,
  streaming: true,
})
```

前端只提交：

```json
{
  "target": "novel.openai",
  "path": "/chat/completions",
  "body": {}
}
```

中继层统一处理：

- 目标、路径和 HTTP 方法白名单；
- 超时和 AbortSignal；
- 请求体和响应体大小限制；
- 禁止客户端覆盖 `Host`、`Authorization` 等敏感请求头；
- 服务端密钥注入；
- JSON、SSE 和二进制响应；
- 结构化错误转换。

对于 GPT 图片 multipart、TTS 音频保存等带有文件副作用的请求，继续保留轻量 provider adapter，不必为了追求“零业务接口”而强行塞进通用代理。

## 9. 可靠性与安全底线

即使是本地单用户程序，也建议至少实现：

- 默认只监听 `127.0.0.1`，用户明确开启后才允许局域网访问。
- LAN 模式使用启动时随机 token 或配对码。
- 校验 `Origin`，防止其他网页直接操作本地服务。
- 不接受客户端文件路径作为数据存储位置。
- 动态实体 ID 使用 UUID 或严格字符白名单。
- 所有文件目标路径执行 `resolve + subpath` 检查。
- 密钥字段读取时返回掩码或 `configured: true`，避免直接回传完整密钥。
- 写入失败必须让接口失败，禁止静默吞错。
- 损坏文件移动为 `.corrupt-时间戳`，不能自动当成空数据。
- SSE 只发送资源版本和变更信息，前端按需重新读取。

### 9.1 原子写入建议（已实现）

已由 `storage/json-file.ts` 实现：同目录临时文件写入 + fsync + `.bak` 备份 + rename 替换，只有磁盘提交成功后才更新缓存并返回。细节以代码为准。

### 9.2 资源级串行队列（已实现）

已由 `storage/resource-lock.ts` 实现：`resourceLock.run(key, task)` 保证同一资源的读改写串行。revision 断言在队列内执行（待第三阶段信封结构落地后接入）。

单文件集合锁定资源 key；EntityStore 可以分别锁定实体 ID，并对新增、删除和列表元数据使用集合级锁。

## 10. 数据版本与迁移

建议区分两种版本：

- `storageVersion`：通用信封和磁盘布局版本，由后端存储层管理。
- `schemaVersion`：业务对象字段版本，由业务所有者管理。

对于前端拥有的数据，前端加载后执行 schema 迁移，再以新 revision 写回。对于后端消费的数据，迁移函数注册在 SettingsRegistry 或对应后端服务中。

示例信封：

```json
{
  "storageVersion": 1,
  "revision": 8,
  "updatedAt": 1786694400000,
  "value": {
    "schemaVersion": 2
  }
}
```

现有发布迁移脚本会保留整个 `data` 目录，因此业务数据迁移仍应在应用启动或首次读取资源时执行，而不能依赖发布脚本覆盖数据文件。

## 12. 验收标准

完成改造后应满足：

- 新增一个纯前端业务集合时，只需注册资源 ID，不需要新增一套后端 CRUD。
- 前端业务字段变化不要求修改通用存储接口。
- 后端消费的数据仍有唯一、明确的 schema 来源。
- 两个页面并发保存不会静默覆盖数据。
- 写入过程中退出程序不会留下半个 JSON。
- JSON 损坏不会被解释为空数据并覆盖原文件。
- 客户端无法通过资源 ID 构造任意磁盘路径。
- 客户端无法借助请求中继访问未注册的网络目标。
- 删除任务、图片和媒体文件时仍能正确执行对应生命周期逻辑。
- 小说和 TTS 项目不再需要后端字段级 CRUD。
- 旧版本 `data` 数据能够自动升级或通过兼容层继续读取。

## 13. 最终边界

最终推荐形成四类后端能力：

1. **通用存储 API**：负责前端拥有的 JSON 数据。
2. **注册式配置 API**：负责后端会消费的设置和密钥。
3. **专用能力 API**：负责任务、图片、音频和本机目录。
4. **受限请求中继**：负责跨域请求，不提供任意代理。

该边界保留了原聊天方案中最有价值的思想——后端不重复理解前端业务字段——同时修正了并发覆盖、数据损坏、密钥泄露、文件生命周期和局域网访问等问题。
