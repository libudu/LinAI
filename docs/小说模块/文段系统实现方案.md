# 小说模块「文段（Artifact）系统」实现方案

> **状态：已全部实施完成（阶段 1~4，2026-08）**。实施过程中的实际决策与本文档的偏差记录见第 11 节；第 10 节附录是改造前现状的快照，文件清单以仓库现状为准。

> 核心思想：**文段是一等公民，对话不是**。用户上传的小说、AI 解析的设定、续写大纲、正文、摘要，统一为「文段」；每次生成都是「参考若干文段 → 产出一个新文段」，文段记录自己的来源（inputs），后续生成只引用文段产物，不依赖对话历史。
>
> UI 形态：**工作区画布**。大纲与正文各成一条竖向节点链（杀戮尖塔节点图的感觉），连线表达「参考 → 产出」的关系；点加号节点生成文段，点已有节点打开模态框继续对话修改。节点只是概念，视觉上就是卡片。

## 1. 现状与差距

### 现状（已经做对的）

现有实现与文段思想的距离比看起来近：

- `NovelText` 已经把 ref / setting / outline / content / summary 统一为一种结构，靠 `type` 区分 —— 这就是文段的雏形。
- `sourceIds` 已经实现了生成溯源（生成时引用了哪些文本的快照）。
- 业务编排全部在前端 `service/`，后端只做基础设施（storage / settings / relay 三个注册项），没有小说专用路由 —— 这正好符合「Artifact 层与模型层解耦」的目标，**本方案后端零改动**。

### 差距（需要调整的）

| 方面           | 现状                                      | 目标                                                                                       |
| -------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| 命名与心智模型 | `NovelText` / `texts`，"文本"是章节的附属 | `NovelArtifact` / `artifacts`，文段是可独立引用、传递的资源                                |
| 生成入口       | 8 种 `GenerateKind`，按场景硬编码         | 收敛为 4 种操作，"生成什么"由输出文段类型决定，"参考什么"由勾选文段决定                    |
| 主界面         | 左栏资源面板 + 章节时间线列表             | 工作区画布：大纲/正文两条竖向节点链 + 连线 + 加号占位节点；参考文/设定等在侧栏资源区       |
| 上下文选择     | 右侧抽屉（ContextDrawer），按章节维度勾选 | 模态框对话，按任意文段勾选（章节维度只是分组快捷操作）                                     |
| 对话           | 无对话                                    | 每个文段节点可挂对话（点入节点继续之前的对话），但对话只服务该节点的修改，永不流入下游生成 |
| 修改方式       | 整段重生成 / 选段重写（字符区间）         | AI 返回结构化编辑操作（patch），前端应用、diff 预览、用户确认                              |
| 版本           | 无版本概念，改了就覆盖                    | 文段带 `version`，保留历史快照，可回退、可对比                                             |

### 明确不做的

- **不做虚拟文件系统**：文段之间是语义引用关系（DAG），不是目录树。内部命名用 artifact，UI 中文叫「文段」。
- **不做自由画布**：不引入 reactflow 等画布库（项目无此依赖），不做拖拽摆位。两条竖列是确定性布局，CSS 列 + SVG 连线即可。
- **不做全局持久对话**：对话按文段挂载、沙箱化（见第 5 节），不存在一个贯穿全书的聊天流。
- **不做完整 Agent 框架**：不引入 LangGraph 之类，远期如需 Agent 工具层（list / search / read / edit 循环）再在本方案的 Artifact API 上加薄薄一层。
- **不做旧数据迁移**：仓库已有约定「小说模块暂不考虑兼容旧数据」，字段重命名直接改。

## 2. 目标数据结构（`src/shared/novel/types.ts` 重写）

简化原则：一次纯重命名 + 语义收敛，不引入新实体、不改变存储粒度。画布所需的连线和占位节点全部由现有字段**派生**，不新增存储。

```ts
// 文段类型：沿用现有五类。对话记录里建议的开放 type/subtype 暂不引入，
// 封闭联合足够覆盖当前全部场景，扩展时加成员即可
export type ArtifactType =
  | 'ref' // 用户上传的参考文（原小说）
  | 'setting' // 核心设定（人物、世界观等；定位灵活，用户自行命名）
  | 'outline' // 章节大纲
  | 'content' // 章节正文
  | 'summary' // 章节摘要

// 文段：一切可引用、可生成、可修改的文本资源（原 NovelText）
export interface NovelArtifact {
  id: string
  type: ArtifactType
  title: string
  content: string
  chapterId?: string // outline/content/summary 归属的章节；ref/setting 无
  // 生成该文段时引用的文段 id 列表（原 sourceIds，语义不变）。
  // 这是 Artifact DAG 的边：本方案不单独建 Relation 表，
  // 反向查询（"谁引用了我"）由前端遍历全部 artifacts 派生
  inputs: string[]
  version: number // 新增：从 1 开始，任何内容修改 +1（阶段 4 的版本历史以此对齐）
  // 该文段节点上的对话记录（阶段 2，见第 5 节）。
  // 沙箱规则：只用于修改本节点，任何 generate 的上下文组装都不读它
  messages: ChatMessage[]
  estimatedTokens?: number
  originalLength?: number // 仅 ref：截断前原始字符数
  createdAt: number
  updatedAt: number
}

// 章节容器：维持现状不动。
// 它已经是极简的分组容器；不把章节本身做成文段（避免自引用层级，收益不大）。
// 画布上章节的"竖向顺序"= chapters 按 createdAt 排序（沿用现状）
export interface NovelChapter {
  id: string
  title: string
  createdAt: number
  updatedAt: number
}

export interface Novel {
  id: string
  title: string
  chapters: NovelChapter[]
  artifacts: NovelArtifact[] // 原 texts
  recentFullChapters: number // 语义变化：从"默认携带最近 N 章全文"降级为"默认勾选的上限保护"（见第 3 节）
  createdAt: number
  updatedAt: number
}

// 上下文勾选：字段改名，形状不变
export interface ContextSelection {
  artifactIds: string[] // 原 textIds
}
```

`NovelIndexItem` / `NovelSummary` / `ChatMessage` 不变。

### 存储层：不动

- 后端 `module/novel/storage.ts` 的 `EntityStore('novel.books')` 注册不变，仍是整本 JSON（`data/novels/books/<id>.json`）读改写。
- 已知的粒度痛点（一字修改整本读写）**本方案不解决**。拆成「每文段一个实体文件」会引入书籍与文段两个资源的一致性问题，与简化目标冲突；待版本历史落地后数据量真的成为问题时再评估，届时 `artifact` 已有独立 id，拆分是纯存储层改动。
- 前端 `api.ts` 的 `createText/updateText/deleteText` 改名为 artifact 版本，机制不变（`mutateEntity` 整本读改写）。

## 3. 生成模型收敛：8 种 kind → 4 种操作

对话记录的关键洞察：**「生成什么」是输出文段的类型属性，「参考什么」是 inputs，两者都不该硬编码成场景枚举**。当前 8 种 `GenerateKind` 收敛为：

```ts
export type ArtifactOperation =
  | 'generate' // 参考 inputs 生成新文段，产出类型由 outputType 指定
  | 'revise' // 按指令整体修改某文段 → version +1（原 revise-outline / revise-content / setting 编辑的 AI 场景）
  | 'continue' // 续写 content 文段（拼接，version +1）
  | 'rewrite-range' // 选段重写（原 rewrite-selection，字符区间替换，version +1）

export interface GenerateRequest {
  op: ArtifactOperation
  outputType?: ArtifactType // 仅 generate：setting / outline / content / summary
  targetId?: string // revise / continue / rewrite-range 的目标文段
  chapterId?: string // generate outline/content/summary 时归属章节
  instruction?: string // revise 的修改指令；generate 的附加要求
  range?: { start: number; end: number } // rewrite-range
  selection: ContextSelection
}
```

映射关系：`setting/outline/content/summary` → `generate + outputType`；`revise-outline/revise-content` → `revise`；`continue-content` → `continue`；`rewrite-selection` → `rewrite-range`。

UI 标题仍然说人话（「生成大纲」「生成正文」），但底层都是同一个 `generate`——新生成的文段自动成为可勾选资源，这就是「文段互相参考、互相生成」的统一感。

### 默认勾选规则（`service/context.ts` 的 `getDefaultSelection`）

- **生成正文**（定稿）：默认勾选「之前所有章的正文 + 本章大纲」。`recentFullChapters` 降级为上限保护——历史正文超出 N 章时，更早的章节自动改挂摘要，token 估算超预警线时在模态框内提示。
- **生成大纲**：沿用现有默认（设定 + 参考文 + 前章摘要/全文），只是勾选单位从文段维度表达。
- 勾选 UI 从「章节 full/summary/none」泛化为任意文段勾选，章节快捷操作保留（底层展开成 artifactIds）。

影响面：

- `service/generate.ts`：`runGeneration` 的 kind 前置校验 switch 收敛为 4 分支；`persistGeneration` 相应简化（generate 新建 / revise 整体替换 / continue 拼接 / rewrite-range 区间替换），落盘时 `version + 1`、对话消息追加到 `messages`。
- `service/context.ts`：`buildMessages` 的任务段 switch 从 8 收敛为 4；**不读目标文段的 `messages`**（沙箱规则的代码落点）。
- `service/prompts.ts`：8 个任务段模板收敛为 4 个，其中 `generate` 的任务段按 outputType 拼接一小段类型说明。
- `service/intent.ts`：意图分类输出改为 outputType，逻辑不变。

## 4. 工作区画布 UI（阶段 2 核心）

### 布局

```text
┌────────────────────────────────────────────────────┐
│ 项目：XXX小说                          [设置]      │
├──────────┬─────────────────────────────────────────┤
│ 资源区    │   大纲列              正文列            │
│          │                                         │
│ 📖 参考文 │ ┌─────────┐                            │
│ 👤 设定   │ │ 大纲 一  │──────────→ ┌─────────┐    │
│          │ └────┬────┘             │ 正文 一  │    │
│ [+ 参考文]│      ↓                  └─────────┘    │
│ [+ 设定]  │ ┌─────────┐                            │
│          │ │ 大纲 二  │──────────→ ┌ ＋ 正文 ┐ ← 高亮│
│          │ └────┬────┘             └─────────┘    │
│          │      ↓                                  │
│          │ ┌ ＋ 大纲 ┐                              │
│          │ └─────────┘                              │
└──────────┴─────────────────────────────────────────┘
```

- **两条竖列**：左列大纲链，右列正文链。节点视觉上是卡片（标题 + 类型 tag + 字数 + 版本号 + 内容预览几行）。
- **连线**（全部派生，不存储）：
  - 大纲 → 右侧同章正文（或正文加号）：`chapterId` 相同。
  - 大纲 → 下一章大纲加号：章节顺序（`chapters` 按 createdAt 排序）。
  - 可选：选中某节点时，把它的 `inputs` 来源节点高亮/描边，让「互相参考」可见。
- **加号占位节点**（虚拟，不落盘）：
  - 每列末尾各一个加号；最新大纲无正文时右侧出现正文加号。
  - **高亮推荐**：最新章缺大纲 → 高亮大纲加号；有大纲缺正文 → 高亮正文加号。引导「先大纲后正文」的推荐路径，但不强制。
- **类型区分（第 5 点）**：虽然底层都是文段，卡片样式按 type 区分——大纲/正文/参考文/设定各有配色和图标 tag；setting 类的具体定位（人物/世界观/其他）靠用户命名和 tag 展示，不增加子类型字段。

### 交互

- **点加号** → 「生成文段」模态框：标题按产出类型显示（生成大纲 / 生成正文），内含参考文段勾选区（默认规则见第 3 节）、附加指令输入、token 估算条、流式生成区。确认后新节点出现在对应位置。
- **点已有节点** → 该文段的模态框对话：上方文段内容（可手动编辑），下方对话区显示 `messages` 历史，可继续发修改指令（走 `revise` / patch），diff 预览后接受落盘。正文节点另有续写、选段重写入口。
- **资源区**（参考文/设定）保留在左侧栏，不进入画布——它们是「原料」，不是「产物链」。新增/编辑同样走模态框。
- **删除**：仅允许删最后一章的大纲/正文（沿用现状约束），连线自动重排。

### 实现要点

- 布局是确定性的两列，不需要画布库：两个 CSS 纵列容器 + 一个绝对定位的 SVG 层画连线（卡片锚点坐标在渲染后测量）。窗口 resize / 节点增删时重算。
- 现有 `Timeline/` 组件被画布取代（OutlineCard / ContentCard 的卡片内部逻辑大量可复用，改的是容器和连线层）；`ContextDrawer` 删除，勾选逻辑迁入生成模态框。
- 生成中状态沿用 store 的 `streaming`（单任务互斥），流式文本渲染在模态框内；模态框关闭后后台继续生成（沿用 AbortController 机制），节点卡片上显示生成中态。

## 5. 节点对话的沙箱规则

用户定稿：点入已创建节点能继续之前的对话。这与「对话不作为正式知识依赖」的原则通过一条硬规则调和：

> **`messages` 只随本节点使用（revise / patch / continue 的上下文可以带最近几轮），任何 `generate` 新文段的上下文组装一律不读任何节点的 `messages`。**

即：对话是「修改这个文段的工作记录」，文段内容才是唯一向下游传递的产物。`buildMessages` 里用代码保证，不靠 prompt 自觉。`messages` 设上限（每文段保留最近 20 轮，超出丢弃最旧），避免整本 JSON 体积膨胀。

## 6. 局部编辑：AI 返回操作而非全文（阶段 3）

对话记录里讨论了三套定位方案：行号（不稳定，弃用）、block 稳定 ID（结构重，暂缓）、搜索定位。**采用搜索/区间定位，block ID 仅记录在案**——小说是自然语言，「找到这段原文并替换」比维护块结构更贴合，且 `rewrite-range` 已经验证了字符区间这条路。

```ts
// AI 通过 revise 返回的编辑操作（流式输出结束后解析为 JSON）
export type ArtifactEditOp =
  | { op: 'replace-text'; find: string; content: string } // find 必须在文段中唯一出现
  | { op: 'insert-after'; find: string; content: string }
  | { op: 'delete-text'; find: string }
  | { op: 'append'; content: string }

export interface ArtifactPatch {
  operations: ArtifactEditOp[]
}
```

流程：

1. 节点模态框里用户发修改指令 → 前端把文段内容 + 指令发给模型（prompt 要求只输出 `ArtifactPatch` JSON）。
2. 前端校验：每个 `find` 必须在当前内容中恰好出现一次；所有操作按顺序在内存中应用。
3. 生成 diff 预览（逐操作展示 旧文本 → 新文本），用户「接受」才落盘（`version + 1`，指令记入 `messages`），「放弃」则丢弃。
4. 校验失败（find 不唯一 / 找不到）时把错误反馈给模型重试一次，再失败则降级为 `revise` 整体重写并提示用户。

何时用 patch、何时用整体 revise：指令明确指向局部（「把第 X 段改成…」「删掉酒吧场景」）走 patch；「整体写得更刺激」这类全局指令仍走整体 revise。选择逻辑先在前端按指令长度/目标文段长度简单启发，不做模型判断。

## 7. 版本管理（阶段 4）

对话记录要求版本管理但明确「不要复制四份巨大文本」。权衡后采用**全量快照 + 数量上限**：patch 链压缩省空间但实现复杂、且小说文段本身不大（正文一般几千字），快照足够。

```ts
export interface ArtifactRevision {
  version: number
  content: string
  source: 'generate' | 'revise' | 'patch' | 'continue' | 'manual'
  instruction?: string // 触发本次修改的用户指令，便于回溯
  createdAt: number
}

// Novel 上新增（与 artifacts 并列）：
history: Record<string, ArtifactRevision[]> // artifactId → 历史版本，不含当前版本
```

- 每次内容修改：旧内容压入 `history[artifactId]`，`version + 1`。
- 上限：每文段保留最近 20 版（content 类 10 版），超出丢弃最旧。
- 能力：节点模态框内查看某版本、回退（旧版本成为新 current，同样记一次 history）、两版本 diff 对比。
- 分叉（branch / fork）：**不做**。「从 v2 分叉出另一版大纲」用「复制文段」手动达成即可。

## 8. 分阶段实施（已全部完成）

### 阶段 1：数据结构收敛（纯重构，无新功能）✅

1. `src/shared/novel/types.ts` 按第 2 节重写（重命名 + `version` / `messages` 字段）。
2. `GenerateKind` 8 → `ArtifactOperation` 4，按第 3 节改 `service/generate.ts` / `context.ts` / `prompts.ts` / `intent.ts`（含正文默认勾选规则调整）。
3. 前端全模块跟随重命名：`api.ts`、`store.ts`、`types.ts`、Timeline / ContextDrawer / ResourcePanel 各组件的 `text(s)`/`sourceIds`/`textIds` 引用。
4. 落盘时 `version` 维护：新建 = 1，任何 update + 1。
5. `npx tsc --noEmit` 通过 + 手动跑一遍现有全部生成场景确认行为不变。

产出：心智模型切换完成，后续阶段只加东西不改结构。

### 阶段 2：画布工作台 ✅

1. 画布容器：大纲/正文两列卡片 + SVG 连线层 + 加号占位节点（含高亮推荐逻辑）。
2. 「生成文段」模态框（点加号）：文段勾选区（章节快捷操作 + 默认规则）、指令、token 估算、流式生成。
3. 「节点」模态框（点已有节点）：内容查看/手动编辑 + `messages` 对话区（沙箱规则落地）+ 发指令走 revise。
4. 资源区侧栏：参考文/设定列表（平铺全部类型文段，可筛选/搜索），新增/编辑走模态框。
5. 删除 Timeline / ContextDrawer，迁移可复用的卡片内部逻辑。

产出：画布形态完整，「文段互相参考、互相生成」的统一交互成立。

### 阶段 3：AI 局部修改（patch）✅

1. `ArtifactEditOp` / `ArtifactPatch` 类型 + prompt 模板（要求模型输出操作 JSON）。
2. 前端 patch 校验与应用器（纯函数：唯一匹配、顺序应用、失败报错）。
3. 节点模态框内 diff 预览 + 接受/放弃。
4. revise 入口按指令启发式选择 patch / 整体重写。

产出：AI 局部修改文段。

### 阶段 4：版本管理 ✅

1. `history` 写入逻辑（每次修改压栈 + 上限裁剪）。
2. 节点模态框内版本面板：历史列表、查看、回退、两版 diff。
3. 「复制文段」（手动分叉）。

产出：方案全部落地。

### 远期（不在本方案内，仅对齐方向）

- Agent 工具层：`artifact.list / read / search / edit / create` 供模型循环调用（届时模型只看到工具，不看到全部文段）。
- 文段全文检索服务化（文段多了以后前端遍历不够时）。
- 多模型路由：Artifact → Task → 多上游（relay 已支持按 target 注册，加 target 即可）。
- block 稳定 ID 编辑模型（patch 的 find 匹配在长文上不可靠时的升级路径）。
- 画布进阶：`inputs` 跨列参考线常显、自由缩放平移（届时再评估是否引入画布库）。

## 9. 风险与注意点

- **patch 的 `find` 唯一匹配**是最脆弱的环节：模型可能复述错原文或命中多处。必须有严格校验 + 一次重试 + 降级整体重写的兜底，绝不允许静默错误应用。
- **对话沙箱规则靠代码保证**：`buildMessages` 不读 `messages` 是一条必须写死在代码里的约束，否则「废案污染下游」的老问题会从节点对话里渗回来。
- **「默认勾选所有历史正文」的上下文膨胀**：上限保护（超出 N 章改挂摘要）+ token 估算提示必须随阶段 2 一起上，不能等用户撞到上下文错误。
- **整本读写改的存储粒度**在对话记录和版本历史上线后体积增长更快（`messages` / `history` 都内联在同书 JSON）。上限裁剪必须与对应功能同时上线；若实测大书 PUT 明显变慢，再评估文段级拆分（见第 2 节）。
- **生成中状态仍在内存**（刷新丢失）：本方案不涉及，如需解决应走通用 TaskService，属另一个独立优化。
- 全程遵守项目约定：pnpm、`npx tsc --noEmit` 唯一检查命令、不跑 build。

### 10.6 实现时容易踩的点

- **流式只在前端内存**：`chatStream` 是 fetch + ReadableStream 手解析 SSE，生成中状态刷新即丢，本方案不管。模态框关闭后生成应在后台继续（AbortController 已在 store 模块级）。

- **summary 由前端算**：`{title, chapterCount}` 写实体时业务方提供，改书名/删章节后要同步。
- **删章节前端级联删 texts**：改 artifact 命名后这条逻辑保留；画布约束「仅可删最后一章」沿用。
- **正文 final 后自动生成摘要**：现有行为，保留；摘要也是文段，生成后应作为可勾选资源出现。
- **新建实体 id 由前端 `crypto.randomUUID()` 生成**。

- `components/NovelTextCard.tsx` 重命名为 `NovelArtifactCard.tsx`。

### 11.2 阶段 2：画布工作台

- 布局采用**行对齐网格**（`grid grid-cols-2`，每章一行两格）而非自由两列：大纲→正文连线恒为横向，无需行对齐计算。SVG 连线锚点渲染后 `getBoundingClientRect` 测量，`ResizeObserver` + window resize 重算。
- **缺大纲的章渲染占位加号入链**（`outlinePlusId(cid)` 兜底），纵向链不断；「最新章缺大纲」的高亮落在该章自己的占位节点上。
- inputs 高亮挂在节点模态框打开态（`nodeModalId`），只画画布上有锚点的来源（大纲/正文）；ref/setting 来源由 ContextTagBar 表达。
- **选段重写改为工具栏按钮**（TextArea 原生 selectionStart/End 取偏移），不再做跟随选区的浮层——比旧 div 方案更简单可靠。
- GenerateModal 流式结束后**自动关闭**（仅当生成由它发起）；模态框关闭后后台生成继续，节点卡片显示生成中态。
- revise 落盘时 messages 记 user 指令 **+ assistant 回复**（阶段 1 只记指令，阶段 2 为实现「点入节点继续之前的对话」补上）。
- `ContextTagBar` 从 `Timeline/` 迁入 `components/`；`Timeline/`、`ContextDrawer/` 已删除。
- 节点对话的 revise **不携带上下文勾选**（用 revise 默认选择）；节点模态框是否加勾选区留待后续评估。
- 暗色主题沿用现有 slate→dark 类映射 + `currentColor`/`var(--app-accent)`，画布为新组件，建议实际切暗色目检对比度。

### 11.3 阶段 3：AI 局部修改（patch）

- **操作定义收敛在 `service/editOps.ts`**（后续重构，原散落在 shared 类型/patch.ts/NodeModal 三处）：每种操作一个 def（`label` UI 标签 + `promptHint` 模型 prompt 示例 + `validate` 入参校验 + `apply` 具体执行），注册进 `EDIT_OP_DEFS`；统一入口 `validateEditOp`/`applyEditOp`（find 唯一性校验在 applyEditOp 统一保证）。`ArtifactEditOp`/`ArtifactPatch` 类型也在此文件（纯前端概念，已从 `src/shared/novel/types.ts` 移出）。**新增操作类型：加 Op 接口 → 加入联合 → 加一项 def**，校验/应用/diff 预览标签/prompt 操作清单全部自动跟随（prompts.ts 的「可用操作」段由 defs 生成）。
- 编排在 `service/patch.ts`：`parsePatch`（容错截取首个 `{` 到末个 `}`，容忍 markdown 代码块）、`applyPatch`（顺序应用，任一失败整体抛错，**不存在部分应用**）、`shouldUsePatch`、`requestPatch`（非流式 `chatOnce`，temperature 0.3，失败带错误重试一次，再失败抛错由调用方降级）。
- **启发式规则**（三条件同时满足才走 patch，否则整体 revise）：①文段 ≥800 字；②指令命中局部信号（第N段/这段/删掉/插入/改成/末尾等）；③不命中全局信号（整体/全文/重写/风格/语气/视角等）。设计取向：误判为 revise 永远安全，规则宁保守。
- diff 预览为逐操作卡片（replace 旧文删除线→新文 / insert-after 定位锚点 / delete 删除线 / append），「接受」才落盘（version+1，messages 记指令 + 结果摘要如「已应用 3 处局部修改」）。
- **已知限制**：patch 请求期间不占 store 的 `streaming` 互斥（非流式本地编排，`patchBusy` 只锁当前模态框）；patch 上下文只有文段全文 + 指令，不读 messages 历史（规则允许，后续可附带最近几轮）。

### 11.4 阶段 4：版本管理

- diff 对比为**自实现行级 LCS**（`utils/lineDiff.ts`，约 60 行，无依赖；相同段 >6 行折叠，行数乘积 >400 万退化为整段替换保底）。未用红绿配色（暗色主题只映射 slate/gray/amber），用删除线 + `−`/`+` 前缀。
- **回退记法**：走正常 content 变更路径（当前内容自动压栈，可再回退回来），`source: 'manual'`，instruction 记「回退到 vN」。
- **generate 覆盖现有文段也压栈记 `'generate'`**（方案字面"generate 是新建"除外，但重新生成覆盖是真实内容替换，不记会导致旧正文彻底丢失）。如要严格排除，删 generate.ts 里三处 `revision: { source: 'generate' }`。
- **rewrite-range 归入 `'revise'`**（枚举五类为方案固化，rewrite-range 语义最接近，代码有注释）。
- 上限：content 类 10 版、其余 20 版，裁剪与写入同点生效；`deleteArtifact`/`deleteChapter` 级联清理孤儿 history。
- 「复制文段」保留 inputs（分叉保留溯源），其余全新（新 id、version=1、messages=[]、无历史、标题加「（副本）」）。
- **已知坑**：每章一条 outline/content 的约束对副本是松的——大纲/正文的副本在画布上无展示入口（`findChapterArtifact` 取数组先者），目前只能靠删掉原文段使用副本，或后续给画布加副本展示。ref/setting 副本在资源区正常可见。
- 摘要文段也累积 history（自动摘要覆写记 `'generate'`），但摘要无版本面板入口，数据留着无害。
