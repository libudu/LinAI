# 数据存储与文件系统说明

> 本文档是 LinAI 文件系统 / 数据存储架构的唯一参考与记录（原《文件系统简化改造方案.md》实施完成后已删除）。内容描述**当前实现**的实现方式、效果与修改方法；细节与代码不一致时以代码为准。

## 1. 总体架构

核心原则：**前端拥有业务数据结构与业务编排，后端提供浏览器缺失的持久化、文件系统与跨域能力**。但后端不是"任意路径文件读写 + 任意 URL 代理"，而是四类能力：

| 后端能力         | 负责的数据                         | 实现位置                          |
| ---------------- | ---------------------------------- | --------------------------------- |
| 通用存储 API     | 前端拥有的 JSON 数据（模板/小说/TTS 项目） | `src/server/common/storage/` + `/api/storage/*` |
| 注册式配置 API   | 后端会消费的设置与密钥（API Key、Base URL、模型 ID） | `src/server/common/settings/` + `/api/settings/:id` |
| 专用能力 API     | 任务、图片、音频、本机目录         | `common/task/`、`common/static/`、各模块专用路由 |
| 受限请求中继     | 跨域请求（白名单目标，非任意代理） | `src/server/common/relay/` + `/api/relay/:target` |

业务归属规则：

- 前端决定字段、业务规则、数据组合关系和业务迁移；后端决定保存位置、原子写入、版本冲突、大小限制和文件权限。
- 后端会消费的数据（任务状态、API 密钥、图片引用、媒体文件操作），后端必须知道其必要结构。
- 只有前端消费的数据（模板、小说内容、TTS 项目），才使用无业务字段假设的通用存储——后端只管信封元数据，`value` 完全由前端定义。

## 2. 通用存储基础层（`src/server/common/storage/`）

| 文件                | 职责                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| `data-path.ts`      | `DATA_ROOT = process.cwd()/data` 与 `dataPath(...segments)`，新代码统一使用，禁止散落 `process.cwd()` 拼接 |
| `json-file.ts`      | 可靠 JSON 读写原语（原子写入、备份、损坏恢复），见 §2.1              |
| `resource-lock.ts`  | `resourceLock.run(key, task)`：同 key 任务按 Promise 链串行，单次失败不阻塞后续 |
| `errors.ts`         | `StorageError`，code：`NOT_FOUND` / `REVISION_CONFLICT` / `CORRUPT` / `READ_FAILED` / `WRITE_FAILED` / `INVALID_RESOURCE` / `PAYLOAD_TOO_LARGE` |
| `registry.ts`       | `storageRegistry.register(id, def)`：资源 ID → 存储驱动与落盘位置的映射，懒建 store 并接线 change bus |
| `resources.ts`      | 资源注册汇总：注册定义在各模块 `module/<模块>/storage.ts`，此处仅副作用导入 |
| `document-store.ts` | 单对象文档存储（供 SettingsRegistry 使用）                           |
| `collection-store.ts` | 小型列表存储                                                       |
| `entity-store.ts`   | 每实体一文件 + 摘要列表                                            |
| `change-bus.ts`     | 资源变更事件总线，见 §2.3                                          |

### 2.1 原子写入与损坏恢复（`json-file.ts`）

写入流程：`mkdir -p` → 写同目录唯一临时文件（`<file>.tmp-<pid>-<ts>-<rand>`）→ fsync → 关闭 → 复制现有文件为 `.bak`（失败忽略）→ `rename` 替换。效果：

- 进程中断不会留下半个 JSON；任何失败清理临时文件并抛 `WRITE_FAILED`，**写入失败必然让接口失败**（全局 onError 映射 500），不存在"假成功"。
- Windows 上杀软/索引器瞬时占用目标文件会导致 rename 偶发 `EPERM/EBUSY/EACCES`，已做短退避重试（5 次，20ms×attempt）。
- 读取时解析失败：文件改名为 `<file>.corrupt-<时间戳>` 并抛 `CORRUPT`，**绝不把损坏数据当成空数据覆盖原文件**；ENOENT 返回 `undefined`。

### 2.2 并发与版本控制

- 同一资源的读改写全部经 `resourceLock` 串行执行；`expectedRevision` 断言在**锁内**完成，不匹配抛 `REVISION_CONFLICT`（409，携带 `currentRevision`）。
- `revision` 由后端在成功提交后单调递增；`updatedAt` 仅用于展示和排序，**不用于并发控制**（时间戳会重复、回拨、时钟不一致）。
- 大小限制：Document/Collection 单 value 默认 256K，Entity value 默认 8M，超出抛 `PAYLOAD_TOO_LARGE`（413）。

### 2.3 变更通知（`change-bus.ts` + SSE）

- 事件形态 `{ resource, revision?, entityId? }`——**只发版本与位置信息，不带数据本体**，前端收到后重新拉取。
- `storageRegistry.register()` 与 TaskService 构造时自动 `changeBus.register(resource)`；只有登记过的资源可订阅。
- 路由 `GET /api/storage/events?resources=a,b`：SSE，`event: change`，30s `ping` 保活。
- 当前只有 `image.tasks` 在前端接入订阅（`GenImage/hooks/useTasks.ts`）；模板/小说/TTS 靠手动刷新 + 409 重试兜底，多标签页不自动同步。

## 3. 三种通用存储模型

信封结构定义在 `src/shared/storage/types.ts`（前后端共享）。信封字段（`storageVersion`/`id`/`revision`/`createdAt`/`updatedAt`）由后端管理，`value`（和 Entity 的 `summary`）完全由前端定义。

### 3.1 DocumentStore — 单对象文档

`StoredDocument<T> = { storageVersion, revision, updatedAt, value }`。只提供 `get()` / `replace(value, expectedRevision?)` **整体替换**（不用 PATCH，整体替换才能准确表达字段删除）。当前消费方只有 SettingsRegistry（§4），不直接暴露 `/api/storage/documents` 路由。

### 3.2 CollectionStore — 小型列表

`StoredItem<T> = { id, revision, createdAt, updatedAt, value }`，集合文件为 `{ storageVersion, revision, updatedAt, items[] }`。

方法：`getSnapshot / create / replace / update(id, fn) / remove / batch(ops, expectedRevision?)`。要点：

- 所有写走集合级锁（key = 文件路径），`batch` 整个批次只写一次文件（模板文件夹重命名等多条修改用它，避免半完成状态）。
- `update(id, fn)` 在锁内读改写，供**后端拥有的数据**使用（TaskRepository 靠它，见 §6）。

### 3.3 EntityStore — 每实体一文件

`StoredEntity<T, S> = { storageVersion, id, revision, createdAt, updatedAt, summary, value }`，落地为 `<dir>/<id>.json`。

- `list()` 只返回 `StoredEntitySummary`（无 `value`），按 `updatedAt` 倒序，不加载正文——小说/TTS 列表页直接渲染摘要。
- 锁粒度：`create`/`remove` 走集合级锁（key = 目录），`replace` 走实体级锁（key = 实体文件）。
- 实体 ID 白名单 `^[A-Za-z0-9_-]{1,64}$`，防路径穿越。
- `readAll()` 对单个损坏文件改名 `.corrupt` 后跳过，不打挂整个列表；`remove` 连带删 `.bak`；迁移失败可重试，非法旧 id 跳过不中断。

### 3.4 已注册资源（注册定义在各模块 `storage.ts`，`storage/resources.ts` 副作用导入汇总）

| 资源 ID           | kind       | 落盘位置                | 注册位置                          | 旧格式迁移                                         |
| ----------------- | ---------- | ----------------------- | --------------------------------- | -------------------------------------------------- |
| `image.templates` | collection | `data/templates.json`   | `module/gpt-image/storage.ts`     | 旧扁平数组首次写入时迁移为信封，旧字段完整保留     |
| `novel.books`     | entity     | `data/novels/books/`    | `module/novel/storage.ts`         | 旧 `data/novels/<id>/novel.json` 一次性迁移，旧目录保留不删；`index.json` 已废弃 |
| `tts.projects`    | entity     | `data/tts/projects/`    | `module/tts/storage.ts`           | 旧 `data/tts/projects.json` 数组迁移，旧文件保留不删 |

客户端只能传资源 ID，不能传真实文件路径（路径注入从根上杜绝）。未注册资源抛 `INVALID_RESOURCE`（404）。

## 4. 注册式设置（`src/server/common/settings/`）

后端会消费的模块配置（API Key、Base URL、模型 ID）走 `SettingsRegistry`，底层复用 DocumentStore。

- 注册定义在各模块 `src/server/module/<模块>/settings.ts`：`{ file, defaults, schema, migrateLegacy?, loadLegacy? }`——**zod schema 是字段的唯一定义来源**，落盘沿用各模块自己的 `config.json`（自动迁移为信封结构；`loadLegacy` 兼容更旧的全局 `data/config.json`）。
- 已注册 id：`gpt-image`（`data/images/config.json`）、`novel`（`data/novels/config.json`）、`tts`（`data/tts/config.json`）。
- 通用路由 `GET/PUT /api/settings/:id`（`api/common/settings.ts`），`put` = 深合并 defaults → `schema.parse` → `replace(value, expectedRevision)`；变更发布到 change bus 的 `settings.<id>`。
- **密钥明文回传**：本应用前后端均在用户本地，GET 返回完整密钥方便查看复制（不要加掩码逻辑）。
- gpt-image 的生效密钥按当前接入点从 keychain 派生：`src/shared/gpt-image/endpoints.ts` 的 `resolveGptImageApiKey`（预设 keychain → 自定义 endpoint key → 平铺字段兜底），前后端共用。
- 迁移样板 helper：`asLegacyRecord` / `pickLegacyFields`。

## 5. 受限请求中继（`src/server/common/relay/`）

不开放任意 URL / 任意头 / 任意方法代理。`RequestRegistry` 按 target 注册白名单：

- 客户端只提交 `{ method?, path, body? }` 到 `POST /api/relay/:target`，**不能设置任何请求头**。
- origin 由服务端解析（常量或设置），拼接后 `url.origin !== origin` 即拒（防 `//host` 逃逸）；方法与路径**精确**白名单（越权路径 403、越权方法 405、未注册 target 404）。
- `injectCredential` 服务端注入密钥；`injectBody` 字段权威覆盖客户端同名字段（如 `novel.openai` 的 `model`）。
- 请求体限 2M，非流式响应限 8M，默认超时 60s；`streaming: true` 且 `body.stream === true` 时 SSE 逐事件透传，客户端断开联动中断上游；上游 4xx/5xx 提取 `error.message` 透传状态码。
- 已注册 target（注册定义在各模块 `relay.ts`，`common/relay/resources.ts` 副作用导入汇总）：`novel.openai`（`module/novel/relay.ts`，OpenAI 兼容 `/chat/completions`，流式，超时 120s）与 `inworld`（`module/tts/relay.ts`，音色列表 + 试听，GET，origin 固定 `https://api.inworld.ai`）。
- **保留专用适配器不走中继**（带文件副作用或业务预处理）：gpt-image 生图（multipart + 落盘）、inworld 音频生成（落盘）、chat/style-analyze（本地图片转 base64）、余额查询（quota 结构换算）、yunwu-token（凭据在前端请求头透传）。

## 6. 任务专用服务（`src/server/common/task/`）

- `repository.ts` `TaskRepository`：只负责任务记录持久化，**私有**复用 `CollectionStore<TaskRecord>`（`data/tasks.json`），**不注册到 storageRegistry**——前端无法经 `/api/storage` 写任务。旧格式迁移含 `rawTemplate → inputSnapshot` 改名。
- `service.ts` `TaskService`：`createTaskFromSnapshot / updateTask / updateTaskStatus / deleteTask(id, keepImage?)`；状态流转、输出文件清理（删除任务时清理 `/api/static/` 前缀的输出文件）、启动恢复（中断的 pending/running 标记失败，一次落盘）、变更发布 `image.tasks` 事件。合并更新剥离 `id`/`createdAt`；写盘失败上抛（NOT_FOUND 除外）。
- 任务状态只能通过 TaskService 变更，保证状态、错误信息、输出文件和 SSE 通知一致。前端接口仅 `GET /api/task` + `DELETE /api/task/:id?keepImage=` + 订阅 `image.tasks` 事件后重新拉取。
- 生图接口 `/api/gptImage/generate` 只接收完整快照 `input`（不再有 `templateId` 参数）；任务中的快照字段为 `inputSnapshot`（`TaskInputSnapshot`，`src/shared/image/template.ts`），是创建时的不可变快照，不是对模板存储的引用。

## 7. 前端封装（`src/client/service/`）

| 文件          | 导出                  | 用法要点                                                                 |
| ------------- | --------------------- | ------------------------------------------------------------------------ |
| `storage.ts`  | `collectionClient(resource)` | `list/create/replace/remove/batch`，错误抛 `StorageApiError`（携带 `code`） |
|               | `entityClient(resource)`     | `list/create/get/replace/remove`；PUT 省略 `summary` 时后端保留现有摘要 |
|               | `mutateEntity(client, id, mutate, summaryOf)` | 读改写标准封装：GET → structuredClone → mutate → 带 revision 整体 PUT；409 自动重取重放一次；mutate 内业务错误不重试 |
| `settings.ts` | `settingsClient(id)`    | `get(): {revision, value}` / `put(value, expectedRevision?)`             |
| `relay.ts`    | `relayRequest(target, ...)` | 仅非流式；流式由 `Novel/service/llm.ts` 直接 fetch + 手写 SSE 解析       |

前端实际使用方：模板 `GenImage/service/templates.ts`（collectionClient）；小说 `Novel/api.ts`、TTS 项目 `GeminiTTS/service/projects.ts`（entityClient + mutateEntity）；三个模块 store 用 settingsClient；`Novel/service/llm.ts`、`GeminiTTS` 音色列表/试听用 relayRequest。

## 9. 全局错误处理

`src/server/index.ts` 注册全局 `app.onError`，统一错误响应 `{ success: false, error: { code, message, ...details } }`：

- `NOT_FOUND` / `INVALID_RESOURCE` → 404；`REVISION_CONFLICT` → 409（携带 `currentRevision`）；`PAYLOAD_TOO_LARGE` → 413；`CORRUPT` / `READ_FAILED` / `WRITE_FAILED` → 500。
- `ZodError` → 400（`VALIDATION_FAILED`）；其他 → 500（`INTERNAL_ERROR`）。
- 底层**禁止**捕获错误后返回空数组/空对象——读取失败、解析失败、不存在、版本冲突必须是不同的错误状态。

## 10. 安全边界（本地应用仍需遵守）

已实施：

- 不接受客户端文件路径作为数据存储位置（storage/settings/relay 均只接受注册 ID）。
- 动态实体 ID 严格字符白名单（§3.3）。
- 文件目标路径执行 `resolve + subpath` 检查（media-classifier / static / chat 图片解析）。
- 写入失败必须让接口失败；损坏文件隔离为 `.corrupt`；SSE 只发版本信息。
- 请求中继白名单制，无任意代理（§5）。

**未实施（局域网加固，开启局域网访问前必须先做）**：默认只监听 `127.0.0.1`、LAN 模式随机 token/配对码、`Origin` 校验。当前版本假定本机受信任环境（密钥明文回传也依赖此前提）；如需开启局域网访问，先实施这三项并重新评估密钥回传策略。

## 11. 数据版本与迁移约定

- `storageVersion`：信封与磁盘布局版本，后端存储层管理；`schemaVersion`：业务对象字段版本，业务所有者管理。
- 前端拥有的数据：前端加载后执行 schema 迁移，再以新 revision 写回。后端消费的数据：迁移函数注册在 SettingsRegistry（`migrateLegacy`/`loadLegacy`）或对应后端服务。
- 旧格式迁移在**首次读取/写入资源时**执行（发布迁移脚本保留整个 `data` 目录，不能依赖它覆盖数据文件）；旧数据保留不删，可手动清理。

## 12. 怎么修改（操作指南）

### 12.1 新增一个纯前端业务集合（如新的列表型数据）

1. 在所属模块新建/编辑 `src/server/module/<模块>/storage.ts`：`storageRegistry.register('模块.资源名', { kind: 'collection', file: dataPath(...) })`，如有旧数据写 `migrateLegacy`；并在 `src/server/common/storage/resources.ts` 加一行副作用导入（与 settings 同一模式）。
2. 前端 `collectionClient<YourValue>('模块.资源名')` 直接读写；字段由前端 zod schema 自定，**无需新增任何后端 CRUD**。
3. 多条原子修改用 `batch(ops, expectedRevision)`。

### 12.2 新增一个实体型资源（大对象、列表只要摘要）

同上但 `kind: 'entity', dir: dataPath(...)`；前端用 `entityClient` + `mutateEntity` 做读改写，业务修改、摘要计算都在前端完成。实体 ID 必须满足白名单。

### 12.3 新增一个后端会消费的配置模块

1. 新建 `src/server/module/<模块>/settings.ts`：`settingsRegistry.register('<id>', { file, defaults, schema, migrateLegacy?/loadLegacy? })`，并导出异步的内部 getter。
2. 在 `src/server/common/settings/resources.ts` 加一行副作用导入。
3. 前端模块 store 经 `settingsClient('<id>')` 读写。**不要**再自写 `/config` 路由。

### 12.4 新增一个跨域请求目标

在所属模块新建/编辑 `src/server/module/<模块>/relay.ts` 注册 target（origin、方法/路径白名单、凭据注入、是否流式），并在 `src/server/common/relay/resources.ts` 加一行副作用导入。有文件副作用（落盘、multipart、本地文件预处理）的请求**不要**塞进中继，保留专用适配器。

### 12.5 修改已有通用存储数据的字段

通用存储接口本身不用改——改前端的业务类型/校验/迁移即可（`src/shared/` 下对应类型 + 前端 store/service）。注意存量数据需要前端加载时迁移（§11）。

### 12.6 修改任务相关行为

只能改 `TaskService`（状态机、清理、恢复），不要开放任务资源到通用存储 API。

## 13. 已知小遗留

- SSE 事件订阅只有 `image.tasks` 接入；模板/小说/TTS 多标签页不自动同步（单用户本地应用可接受）。
- 日志器在 `src/server/common/logger.ts`（落盘 `data/logs/`）；如需按模块拆分日志文件，直接 `new Logger('<id>')`。
